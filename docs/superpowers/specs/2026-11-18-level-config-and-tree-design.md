## 1. 要做什么、为什么

现在染色迷宫的 80 关写死在代码里（`src/game/levels.ts`），想改一张图就得改代码、重新部署。
要做成和 demon 一样：**关卡在网页上配置，点「发布」后所有玩家就能玩到**。同时把选关从"弹出的面板"换成"上下滚动的一棵树"。

1. **配置页** <https://coloring-maze.dengjiabei.cn/config>：每一关的地图大小、墙（遮挡物）、起点、染料颜色都能配；
   现有 80 关直接回显，可以改了再发布；可以新增、删除关卡，可以调整顺序。
2. **选关树**：打开网站先看到一棵刻在长木板上的树，一关一个节点，上下滚动；通过的关可以重玩，
   轮到的那一关可以点，后面没轮到的关点不动。不再有弹出的选关面板。
3. **长方形地图的横竖**：不做"手机一套、电脑一套"的配置。地图只配一份；长方形的图在宽屏上横着摆、
   在竖屏上竖着摆（转 90°）。这个现在已经是这样做的，新配的图走同一套逻辑。

## 2. 已经定下来的事

| 事项 | 结论 | 谁定的 |
| --- | --- | --- |
| 打开网站先看到什么 | 树就是首页；点一关才开始；通关后可以「下一关」直接继续，也可以回到树上 | 你选的 |
| 关卡增删 | 新增、删除、调顺序都要 | 你选的 |
| 树的画风 | 木刻风：一块很长的胡桃木板，树是刻在、嵌在板上的图案，每一关是嵌在枝头的圆木片 | 你选的 |
| 手画地图的检查 | 保存时检查能不能通关；通不了就提醒，并给出"改哪几格"的建议，改动尽量小，改完保证没问题 | 你说的 |
| 横竖 | 不加手机/电脑两套配置，按地图比例和当前屏幕自动转 | 你说的 |
| 发布要口令 | 和 demon 一样：进配置页先输管理口令，读公开、写要口令 | 我定的（照参考项目） |
| 地图大小 | 行、列各 5–23；长边最多 23，短边最多 17 | 我定的，理由见 6.1 |
| 染料颜色 | 现有的 8 种染料色一点即选，另加一个自选颜色 | 我定的 |
| "可能走进死局"怎么办 | 只提醒、不拦，提醒时同样给修改建议 | 我定的，理由见下 |
| 中途插进新关，老玩家怎么办 | 不把老玩家卡回去：通过的关照样能玩，新插的关和原来轮到的关都能点 | 我定的，见 6.4 |

**关于死局，为什么是"只提醒"**：内置 80 关除了"能通关"，还保证"无论怎么走都不会走进死局"。
后面这一条用的是一个保守的判断（`shortfall`）：它说"没问题"就一定没问题，但它说"有风险"的图不一定真有死局。
拿它当硬门槛，会把一部分其实没毛病的手画图也拦下来，还会显示一句不准确的"会走进死局"。所以：

- **通不了关 → 拦**，给修改建议。这一条是精确的。
- **不能保证不走进死局 → 提醒**（文案是"不保证不会走进死局"），同样给修改建议，采不采用随你，照样能发布。游戏里有撤销和重玩。
- 修改建议的目标始终是"改完之后保证没问题"——既能通关，又保证不会走进死局。

想改成"必须保证不走进死局才能发布"的话告诉我，只是把提醒换成拦。

## 3. 不做的事

- 不做手机/电脑两套地图配置（你明确说了不要）。
- 配置页只按电脑屏幕做（1280×800 以上），不做手机版排版——和 demon 的编辑器一样。
- 不做账号体系：只有一个管理口令。
- 不照搬开心消消乐的画面。借用的只是"沿着一棵树往上、一关一个节点、上下滚动"这个形式，
  树、木片、背景都按染色迷宫自己的木头风格重新设计。
- 下面这些是我想到、但你没提的，**默认不做**，要的话告诉我：
  关卡数据导入/导出、配置页里试玩、发布历史与回滚界面、未发布的修改自动存草稿。
  （其中"回滚"在服务端留了一手，见 6.2，但不做界面。）

## 4. 现状（和这次改动有关的部分）

- **部署**：Cloudflare Workers 静态资源（`wrangler.jsonc`，`npm run deploy` = 构建 + `wrangler deploy`），
  纯前端，没有服务端代码，没有任何网络请求。
- **关卡**：`src/game/levels.ts` 是生成出来的 80 关（`rows` 字符画 + `par` 最少步数 + `solution` 一种最少步数的走法）。
  染料颜色不在关卡里，按关卡序号从 8 种颜色里轮着取（`src/view/dyes.ts`）。
  直接引用 `LEVELS` 和 `dyeOf/dyeCss` 的只有 `src/app.ts`；界面（`src/ui/hud.ts`）是靠参数拿到的。
- **最少步数怎么来的**：前 50 关用搜索（`src/game/solver.ts`）；比 15×15 大的图用整数规划
  （`tools/mip.ts`，开源求解库 HiGHS 的 WebAssembly 版，目前只在 Node 里跑）。
  整数规划在任何大小的图上都能用，几毫秒到几十秒一张；图通不了关时它会明确回答"无解"。
- **`shortfall(level)`**（在 `solver.ts` 里）：只分析"停靠点"之间怎么连，不用搜索，一两毫秒一张图。
  返回 0 表示"既能通关、又保证不会走进死局"；大于 0 表示"不能保证"——可能通不了关，也可能只是有走进死局的风险，
  也可能其实没事（它是保守的）。数字越大离"有保证"越远。
  关卡生成器的"修补"造法（`tools/gen.ts` 的 `mend`）就是靠它一格一格把图改到 0 的。
- **形状上的两条硬要求**（`src/game/shape.ts`）：地面连成一片；墙不能只在角上相碰。不满足的话托盘的轮廓描不出来。
- **选关**：`index.html` 里的 `#levels` 面板 + `src/ui/hud.ts` 的 `openLevels`，点「选关」按钮弹出。
- **存档**：`localStorage['coloring-maze.v1']`，`best[i]` 按关卡**序号**记最好步数（`src/game/progress.ts`）。
- **横竖**：`src/app.ts` 的 `facing()`，进入一关时看留给托盘的地方是横是竖，必要时把图沿对角线翻过来（`transposeDef`）。
- **木纹**：启动时显卡画好三张木纹；界面用的两张通过 CSS 变量 `--wood-dark`、`--wood-light` 给 DOM 用。
- **取景**：`src/view/stage.ts` 按"墙高不超过 0.85"留的余量（`TALLEST`）。墙高是 `0.34 × 格子边长 + 0.12`，
  格子边长是 `10 ÷ 长边格数`，所以长边不到 5 格时墙会高出取景范围。

## 5. 几种做法的取舍

### 5.1 最少步数在哪里算

| 做法 | 取舍 |
| --- | --- |
| **在配置页的浏览器里算（选这个）** | HiGHS 本来就支持浏览器；放进 Web Worker 里算，界面不卡。大图要等几秒到一两分钟。只有配置页会下载那 3.5 MB 的求解库，玩家不受影响 |
| 在服务端（Worker）算 | Worker 的 CPU 时间有限额，大图算不完 |
| 不算，只显示"参考步数" | 星级就没有依据了，和现有 80 关的标准不一致 |

服务端在发布时只做便宜的核对（见 6.2）；"这是不是最少"服务端核不了——只有拿着口令的人能写，信配置页算出来的。

### 5.2 关卡存在哪里

| 做法 | 取舍 |
| --- | --- |
| **Cloudflare KV + 一个很小的 Worker 接口（选这个）** | 和 demon 一样，发布即生效，不用重新部署 |
| 发布时改代码仓库里的文件再触发部署 | 要接 GitHub 和自动部署，重得多；"点发布就能玩"做不到秒级 |

### 5.3 配置页怎么写

demon 的编辑器是一个 4000 行的自包含 HTML。染色迷宫的配置页要用到游戏里已有的代码
（读关卡、形状检查、`shortfall`、整数规划），所以做成 **Vite 的第二个入口**（`config.html` + `src/config/`，TypeScript），
直接复用这些模块，不抄一份。

### 5.4 树怎么画

| 做法 | 取舍 |
| --- | --- |
| **普通网页元素 + SVG（选这个）** | 用浏览器自带的滚动，手机上手感最好；树干、枝、叶用 SVG 按关卡数现场生成；木纹用现成的两张贴图 |
| 画进 three.js 的 3D 场景 | 要自己做滚动的惯性和回弹；80 多个节点的命中判断、文字都得自己画；收益只是光影更真 |
| 一整张 canvas | 80 关的树有近万像素高，手机上超过 canvas 的大小上限，得切块，麻烦 |

## 6. 设计

### 6.1 关卡数据

KV 里存一份、接口收发的都是这个：

```jsonc
{
  "version": 1,
  "levels": [
    {
      "id": "b01",                 // 一关的固定编号：改图、换顺序都不变。存档按它记
      "rows": ["#S..", "...."],    // 字符画：# 墙  . 地面  S 起点（恰好一个）
      "dye": "#2646b8",            // 染料颜色
      "par": 3,                    // 最少步数
      "solution": "ULD"            // 一种最少步数的走法，长度必须等于 par
    }
  ]
}
```

**基本校验**（配置页、服务端、游戏三处用同一个函数，放在 `src/game/levelset.ts`，纯逻辑、无 DOM）：

- 1–200 关；`id` 互不相同，小写字母和数字，2–12 位。
- 行、列各 5–23；长边 ≤ 23，短边 ≤ 17；每行一样长；起点恰好一个。
  （上限 23×17 是现在最大的关，画面、手机上的格子大小、求解时间都实测过；
  下限 5 是因为长边不到 5 格时墙会高出取景范围，而且现有关卡和测试都以 5 为最小。）
- 地面连成一片；没有"只在角上相碰"的墙。
- `solution` 只含 `URDL`，照着走每一步都滚得动、正好染完，步数等于 `par`。**这一条同时就证明了"能通关"。**
- `dye` 是 `#rrggbb`。

**配置页额外做的**（太贵或只是提醒，不放进共用的函数）：算最少步数；`shortfall` 的提醒；修改建议。

内置的 80 关作为**兜底和初始内容**保留在代码里：编号 `b01`–`b80`，染料按现在的轮换规则。
KV 里还没有数据时，游戏和配置页看到的都是这 80 关。

### 6.2 后端：一个 Worker + KV

`wrangler.jsonc` 加上 `main`（Worker 入口 `worker/index.ts`）、KV 绑定 `LEVELS_KV`、
`assets.binding`、`assets.run_worker_first: ["/api/*"]`（本机的 wrangler 4.156 的配置说明里有这几项）。
`/config` 由静态资源的 `html_handling`（默认 `auto-trailing-slash`）直接对应到 `config.html`，不用写重写规则。

| 方法 | 鉴权 | 作用 | 响应 |
| --- | --- | --- | --- |
| `GET /api/levels` | 无 | 读线上关卡 | 200 关卡 JSON；404 `{error:"not_found"}`（还没发布过）。`Cache-Control: no-store` |
| `POST /api/levels` | `Authorization: Bearer <口令>` | 只验口令（配置页进门用） | 200 / 401 |
| `PUT /api/levels` | 同上 | 发布 | 200 `{ok:true,count}`；401；400 `{error:"invalid",detail,level}`（`level` 是出错的那一关的序号） |
| 其它 | | | 405 |

- 口令是 Worker 的密钥 `LEVEL_ADMIN_TOKEN`；没配这个密钥时一律拒绝写入（忘了配不等于谁都能写）。
- **按 Cloudflare 免费版的限额来设计**：免费版每次请求只有 10 毫秒 CPU。所以发布时服务端只跑 6.1 的"基本校验"
  （200 关估计两三毫秒），不跑 `shortfall`、不算最少步数。请求体超过 1 MB 直接拒绝。
  实施时先查一遍 Cloudflare 当前的限额文档；如果账号是付费版，这一条仍然成立，只是余量更大。
- KV：键 `levels` 存当前版本。每次发布前把旧的那份另存到键 `levels:prev`——万一发错了，我可以用 wrangler 手动恢复。不做界面。
- 接口的处理函数写成纯函数 `handle(request, env)`，KV 用一个接口描述，这样测试里可以用假的 KV 直接测。

### 6.3 游戏怎么拿到关卡

启动时（和画木纹、等字体同时进行）请求 `/api/levels`，最多等 2.5 秒：

1. 拿到且通过基本校验 → 用它，并在 `localStorage['coloring-maze.levels']` 留一份；
2. 请求失败、超时、校验不过 → 用上次留的那份（同样要过校验）；
3. 也没有 → 用内置 80 关。

任何一步出错都只在控制台记一句，**不挡游戏启动**。

`src/app.ts` 里所有直接用 `LEVELS[...]`、`dyeOf(index)`、`dyeCss(index)` 的地方改成用启动时得到的那份关卡表；
染料颜色从关卡里取。

### 6.4 存档（v2）和"哪些关能玩"

现在按**序号**记成绩。关卡能改、能换顺序之后，序号就对不上了，所以换成按**关卡编号**记：

```jsonc
// localStorage['coloring-maze.v2']
{
  "done": { "b01": { "best": 3, "sig": "9f3a1c" } },  // sig：当时那张图的指纹（rows 的哈希）
  "muted": false
}
```

- 一关"通过了"= `done` 里有它。通过的记录只增不减；线上已经删掉的关，它的记录留着不管。
- 这一关的图后来被改了（`sig` 对不上）：仍然算通过（后面的关不会突然锁上），但最好步数和星星清掉，重玩才有。
- **哪些关能玩**（一条规则）：**这一关通过了，或者排在它前一位的那一关通过了；排第一的总能玩。**
  其余的都点不动。
  - 平常情况下，这就是"通过的都能重玩，再加上紧跟着的那一关"。
  - 配置页在中间插了一关、或者换了顺序之后：老玩家通过的关照样能玩，原来轮到的那一关照样能点，
    新插进来的那一关也能点（它前一位通过了）。这时树上会有不止一关亮着"轮到你了"的圈。
    例：老玩家通过了前 60 关，第 5 位插进一关——第 5 位的新关能点，第 62 位（原来的第 61 关）也能点。
- 首次升级：把 `coloring-maze.v1` 的 `best[i]` 转成 `b01`–`b80` 的记录（指纹按内置的图算），`muted` 照搬。旧的那份留着不删。
- "多个标签页同时玩，存之前先合并"的做法保留（每关取更好的成绩）。

### 6.5 配置页 `/config`

进门先输管理口令（和 demon 一样：弹层输入 → `POST /api/levels` 验证 → 记在这台电脑的浏览器里；401 时清掉重输）。

```
┌─────────────┬──────────────────────────────┬───────────────────────────┐
│ 关卡  83     │                              │  [ 发布 ]      [返回游戏]   │
│ ┌──┐ 1      │                              │───────────────────────────│
│ │▦▦│ 3 步   │                              │ 第 12 关                   │
│ └──┘        │        格子画布                │ 大小   行 [ 9 ]  列 [ 9 ]   │
│ ┌──┐ 2      │   点一下或按住拖动来画          │ 画笔   ( 墙 ) ( 地面 ) ( 起点 )│
│ │▦▦│ 5 步   │                              │ 染料   ● ● ● ● ● ● ● ●  [自选]│
│ └──┘        │                              │───────────────────────────│
│   …         │                              │ 检查                       │
│ （拖动换顺序） │                              │ ✓ 地面连成一片              │
│             │                              │ ✗ 通不了关：有 3 格染不到    │
│ [＋ 新增关卡] │                              │   建议：把画布上圈出的 1 格   │
│ [ 删除本关 ]  │                              │   改成墙      [ 采用建议 ]  │
│             │                              │ 最少步数   —               │
└─────────────┴──────────────────────────────┴───────────────────────────┘
```

- **左栏**：关卡列表（缩略图、序号、最少步数；不能发布的关标红）。点选切换；拖动换顺序；新增关卡加在最后
  （默认 7×7 的空地，起点在左上角，染料取下一种，编号随机生成）；删除当前关（至少留一关）。
- **中间**：格子画布。选"墙"或"地面"画笔后点一下、或按住拖过去，把格子改成那种；选"起点"后点一格地面。
- **右栏**：
  - 大小：行、列两个数字框。改大多出来的格子是地面；改小就裁掉右边、下边；起点被裁掉时放到第一个地面格上。
  - 染料：8 种现成的 + 自选颜色。
  - **检查**（每次改动后自动重查，在后台线程里算，不卡界面；又改了就作废重来）。按顺序：

    | 第几步 | 查什么 | 不过时 |
    | --- | --- | --- |
    | 1 | 形状：地面连成一片、没有只在角上相碰的墙 | **拦**，圈出有问题的格子，给修改建议 |
    | 2 | 每一格是不是都滚得到（便宜） | **拦**："通不了关：有 N 格染不到"，圈出来，给修改建议 |
    | 3 | 整数规划算最少步数。它回答"无解"的话 | **拦**："通不了关：每一格都滚得到，但没有一条路线能把它们全染上"，给修改建议 |
    | 3′ | 算了 3 分钟还没出结果 | **拦**："这张图太复杂，算不出最少步数，请改小一些或多放几块墙" |
    | 4 | `shortfall` 是不是 0 | **只提醒**："不保证不会走进死局"，给修改建议，可以不理 |

    第 3 步算出来了，就显示"最少 N 步"，这一关可以发布。
  - **修改建议**：在后台找"改最少的格子，就能让这张图形状合格且 `shortfall` 为 0"的办法。
    先试所有"只改一格"的（把某一格墙↔地面互换，或者换个起点），取其中任意一种合格的；
    都不行再往下试改两格、三格……最多六格——格子多了不再穷举，而是每一步只留离合格最近的几种接着试。
    找到了就在画布上把要改的格子圈出来，并写明"把这 N 格改成墙/地面"；点「采用建议」一次改好，然后照常重新检查。
    六格以内找不到就如实说没找到，给一句通用的提示（"小球得有地方能停下来：试试在长通道中间加一块墙"）。
- **发布**：所有关都能发布（上表没有"拦"的项、最少步数都算完）才能点。只重新算改过图的关，
  没动过的关沿用原来的最少步数和走法。成功后提示"已发布，玩家刷新页面后生效（全球同步最长约一分钟）"；
  服务端退回 400 时把出错的关和原因显示出来。
- 有没发布的修改时关页面，用浏览器自带的"确定离开吗"拦一下（这是唯一的确认框；不想要可以去掉）。

求解库的安排：`tools/mip.ts` 的算法挪到 `src/solve/tour.ts`，改成"把加载好的 HiGHS 传进来"的写法，
Node（生成工具、测试）和浏览器（配置页的 Worker 线程）共用一份；`highs` 从开发依赖改成正式依赖，
但只打进配置页的包里，游戏页不引用它。

### 6.6 选关树（首页）

```
        手机（竖屏）                          电脑（宽屏）
┌───────────────────────┐      ┌──────────────────────────────────────────┐
│  ░░ 胡桃木板 ░░░░░░░░░  │      │ 桌面 │ ░░░░ 胡桃木板（居中的一长条）░░░░ │ 桌面 │
│        ╭──(15)        │      │      │            ╭──(15)             │      │
│   (14)─╯   🍃刻的叶子  │      │      │       (14)─╯                   │      │
│        │              │      │      │            │                   │      │
│   (13)─┤  ← 轮到的这关： │      │      │       (13)─┤                   │      │
│        │    亮圈       │      │      │            ├──(12) ★★★ 26 步   │      │
│        ├──(12) ★★★    │      │      │            │                   │      │
│   (11)─┤     26 步     │      │      │       (11)─┤                   │      │
│        │              │      │      │            │                   │      │
└───────────────────────┘      └──────────────────────────────────────────┘
        ↕ 上下滚动：往上是后面的关，最底下是树根和第 1 关
```

- **样子**：一块很长的胡桃木板（用现成的深色木纹），上面刻着一棵树——树干从底下的树根一路弯弯曲曲往上，
  左右交替伸出枝杈，每个枝头嵌一块圆木片（浅色桦木，和现在选关面板里的木片同款，只是圆的）。
  树干、枝杈是刻出来的凹槽（深色的线 + 一道细细的受光边），枝头旁边刻着几片叶子。
  **通过的关，它的叶子会填上那一关的染料颜色**——树是一关一关被"染"出来的，和游戏的主题呼应（这一条是我的设计，不想要可以去掉）。
- **三种木片**（哪种是哪种，按 6.4 的规则）：
  - 通过的：亮的，写着序号、星星、最好步数；可以点，重玩。
  - 轮到的（能玩但还没通过）：亮的，外面一圈亮边；可以点。平常只有一个，见 6.4 的例外。
  - 没轮到的：没打磨的暗木片，只有序号；点不动。
- **滚动**：浏览器自带的上下滚动（手机上手指划、电脑上滚轮）。打开时自动停在**位置最靠上的那个"轮到的"关**附近
  （也就是玩家打得最远的地方）；全部通关了就停在最顶上。
- **手机和电脑**：木板最宽 560 像素左右。手机上铺满屏幕宽度；电脑上是居中的一长条，两边露出深色桌面。
- **流程**：
  - 打开网站 → 树。（3D 的托盘画面这时不渲染，省电。）
  - 点一关 → 树退出去，托盘滑进来、弹珠落下（现有的进场动画）。
  - 关卡里的「选关」按钮 → 回到树（这一局不保留）。
  - 通关面板：「再来一次」「下一关」之外加一个「选关」，回到树上；刚解锁的那一关这时亮起"轮到"的圈。
  - 新手提示牌的规则不变（没通过排第一的那一关的人，在那一关里看到）。
- **拆掉的东西**：`index.html` 的 `#levels` 面板、相关样式、`hud.ts` 的 `openLevels/closeLevels`、
  `app.ts` 里围绕"面板开着时不接受操作"的逻辑，以及对应的测试——换成树的。
  存档里的 `last`（上次玩到哪一关）不再需要。

### 6.8 怎么验证

- **单元测试（vitest）**：
  - 关卡表的基本校验：每条约束一个反例；内置 80 关包成的关卡表能通过。
  - 接口处理函数配假 KV：GET 404/200、POST 401/200、PUT 401/400/200、没配口令时一律 401、发布后留了上一版。
  - 存档：v1→v2 的迁移；改图后成绩清掉但仍算通过；6.4 的例子（中间插一关、换顺序后哪些能玩）。
  - 修改建议：随机造的坏图，采用建议后确实形状合格且 `shortfall` 为 0；只需改一格的情况和穷举对比，确认没有多改。
  - 关卡加载的三级回退。
  - `tests/app.test.ts`：把选关面板的用例换成树的（点得动/点不动、从树进关、通关后回树、轮到的关前移）。
- **内置 80 关的测试保持不动**（它们现在是兜底内容）。整数规划搬家后，原有的核对测试照跑。
- **真浏览器**（puppeteer，本机已有）：本地起带假接口的开发服务器，走一遍"输口令 → 改第 3 关成通不了关 → 看到拦和建议 →
  采用建议 → 新增一关 → 发布 → 回游戏在树上看到新关"；树在手机尺寸和电脑尺寸各截图检查；从树进关、通关、回树。
- **帧率**：树是普通网页元素，进关后的画面没变；仍按新旧两版交替各测 6 轮的办法确认没有变慢。
- **上线后**：`GET /api/levels` 先是 404（游戏用内置 80 关）；配置页发布一次后变 200；错口令 401；游戏刷新后用的是线上那份。

### 6.9 上线要做的一次性配置

1. `npx wrangler kv namespace create coloring-maze-levels`，把得到的 id 写进 `wrangler.jsonc`（我来做）。
   （实施时改的名字：账号里已经有一个叫 `LEVELS_KV` 的命名空间，是 demon 的，不能共用；代码里的绑定名仍是 `LEVELS_KV`。）
2. **管理口令由你自己设**：在 Claude Code 里输入 `! npx wrangler secret put LEVEL_ADMIN_TOKEN`，按提示敲口令。
   这样口令不经过我、不进聊天记录、不进代码仓库。
3. `npm run deploy`。上线后 KV 是空的，玩家看到的仍是内置 80 关；你在配置页点过一次发布之后才切到线上那份。

本地开发：`npm run dev` 里带一个只在开发时生效的小插件，用同一个接口处理函数 + 一个本地 JSON 文件当 KV，
口令固定为 `dev-token`。不依赖 `wrangler dev`（demon 的文档里记过它在 Windows 上要装额外的运行库）。
